- **Auditor:** Claude Haiku 5.5 (single session, adversarial probing only)
- **Scope:** `gritc check` / `gritc run` on the `integration` branch at the state the session started from (HEAD `caf5a60`, working tree clean apart from the scratch folder `attack/`).

1. ### F1 — Recursion through `spawn` is not checked for termination (FB-C33)

Reproducer (accepted by `gritc check`, verdict green):

```text
ƒ f(n: u64) → () ! ∅ ↓ n { spawn(f, n); }
ƒ main() → i32 ! ∅ { f(1u64); 0 }
```

Also accepted (no `↓`, no `div`):

```text
ƒ a(n: u64) → () ! ∅ { spawn(b, n); }
ƒ b(n: u64) → () ! ∅ { a(n); }
ƒ main() → i32 ! ∅ { a(1u64); 0 }
```

Controls showing the hole is specific to `spawn` (all correctly rejected):

- Direct self-recursion with a non-decreasing variant: E0702.
- Mutual recursion where one function lacks `↓`: E0703.
- Recursion through a function value passed as a parameter: E0703.
- Recursion through a function stored in a struct field: E0703.
- Recursion through a function stored in `Option`: E0703.
- Polymorphic recursion growing types without bound: E0312 (no hang).
- Recursion through `Mutex::with` at the same lock level: E0502.

Consequence: D12 requires every recursion to carry `↓` or `div`. A program accepted under this rule is not guaranteed to terminate, and each `spawn` reserves a 256 MiB thread stack, so unbounded spawning can end in `spawn_failed` (exit 70). This is not a memory-safety bug, but it is a broken termination guarantee.

Root cause (hypothesis, from reading ~30 lines of `gt-term`): call-edge construction adds a function-item operand to the escaped set and to the instance graph only when the callee has a body. `spawn` is a bodiless prelude intrinsic, so the edge caller → worker is not created.

The reproducer was **not executed**. The checker verdict is the evidence.

### F2 — `spawn` effect (design question)

- `b01`: `ƒ w(x: u32) → () ! ∅ { }` and `ƒ g() → () ! ∅ { spawn(w, 1u32); }` — accepted.
- Control: a worker declared `! {mem}` called from a `! ∅` function is correctly rejected with E0801 (the effect of `spawn` is the effect of its worker).

So the observed behaviour matches "spawn effect = worker effect". What is undecided is whether the `detach` marker in the prelude signature `spawn(f: ƒ(A) ! {detach}, a: A) ! {detach}` should be enforced on callers. The owner must choose.

## 4. Not done

- F1 was not executed at runtime (resource risk on the test machine). Verdict only.
- The fix in `d220202` and the red test in `f79296e` were not run by this audit.
- Deadlock caused by waiting on another thread while holding a lock: a liveness property, not covered by the current lock-ordering check. Not probed.
- Native stack overflow from deep but statically valid recursion: documented in `KNOWN_LIMITATIONS` (8.I), not probed.
- No full gate run (`tools/gate.sh`).

## 5. Recommendations

1. Owner decides F2 (whether `detach` is enforced on callers).
2. Confirm that `crates/gt-term/tests/spawn_recursion.rs` is red before `d220202` and green after, and run the full gate on the resulting commit. This is required by the contract before FB-C33 is marked fixed.
3. Extend the loop and termination generators with `spawn` and function-typed intrinsic arguments, so the class is covered by the generator and not only by hand-written tests (grit-contract §3.3).
4. Continue probing intrinsics that take function arguments and whose bodies are absent from the prelude. `spawn` is the only such case found by this audit; `Mutex::with` was checked and is handled by lock ordering.
